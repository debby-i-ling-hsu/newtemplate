> 狀態：模板骨架（複製專案後請改寫成本專案的真實功能）
> 性質：**本專案目前實際提供哪些功能、每個功能怎麼運作、做到什麼程度的單一事實來源。**
> 維護規範見 [`../AGENTS.md`](../AGENTS.md) 的「功能規格書」一節。

## 0. 這份文件是什麼，為什麼要維護

這份文件用非工程師也讀得懂的方式，描述本專案**目前**提供哪些使用者可見功能、每個功能怎麼運作、做到什麼程度、邊界與驗收標準。它和程式碼一起維護，目的：

1. **防 VibeCoding 改壞**：動工前先讀本文件，知道既有行為與邊界，才不會改 A 功能時把 B 功能弄掛。
2. **改壞好追蹤**：每次功能變更都在這裡留紀錄，出問題時能對照「本來應該長怎樣」回推哪裡退化。
3. **好跟案主說明**：這是一份非工程師看得懂的功能清單 + 進度表，可直接拿來對焦需求、報進度、驗收與報價。

### 狀態圖例（每個功能都要標一個）

| 狀態 | 意義 |
|------|------|
| ✅ 已完成 | 已實作、跨 Web/Mobile/後台到位並通過驗證，可用。**確認可用才標，不灌水。** |
| 🚧 進行中 | 已動工、部分完成或尚未驗收。 |
| ⏳ 未開始 | 已規劃但尚未動工（含案主剛提出、還沒寫的需求）。 |
| 🗑 已下線 | 曾經有、已移除（保留一行說明何時、為何移除）。 |

> 有 MVP 範圍時，用 `⭐` 標記屬於 MVP 的功能，後期功能不要混進 MVP。

### 維護規則（強制）

- **功能改了，這份就要同一次改**：任何使用者可見功能的新增 / 修改 / 刪除（資料模型、API 契約、畫面/表單、權限、狀態流程、驗收標準），都要在同一次變更更新本文件，並把狀態往前推進。功能改了但本文件沒更新 = 這次變更未完成。
- **案主有新需求要主動更新**：當使用者轉述「案主/客戶那邊有新要求或要修改」時，即使還沒寫程式，也要先把該需求反映進本文件（標 `⏳ 未開始`），讓規格永遠是最新的對焦點，再開始實作。
- **狀態跟著工進走**：開始動工 → 改成 `🚧 進行中`；跨端到位並驗收 → 改成 `✅ 已完成`。第 2 節「功能狀態總覽」要和第 4 節各功能的狀態一致。
- **每筆變更寫進第 5 節變更歷史**。
- 本文件描述「系統現在做什麼、做到哪」；工程規範以 `AGENTS.md` / `docs/PRINCIPLES.md` 為準，衝突時以工程規範為準。本文件與程式碼實際行為牴觸時，以程式碼為準並立即修正本文件。
